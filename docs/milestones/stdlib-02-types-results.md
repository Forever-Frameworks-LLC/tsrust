# S06: generic value types and typed results

Status: in progress; structured annotations and the concrete generic-record compiler/source-editor increment accepted with focused evidence. Generic function specialization, callable containers, Result and checkpoint measurements remain pending. Depends on the S05 primitive registry/build foundation. This file does not reserve or renumber the other compiler track's gates. Before accepting each increment, use the current development workflow and preserve its checkpoint evidence.

## Intended source behavior

Users can declare generic functions and named containers, call them with inferred or explicit type arguments, and receive a typed Result<T, E> from fallible standard-library operations. A result contains exactly one success or error payload. Checking its discriminant proves which payload may be accessed. Success/error construction, branching, forwarding and early return preserve ownership; no implicit clone or arbitrary dynamic value erasure is allowed.

Callable record fields now support owned source declarations, construction, invocation, moves and replacement; editor acceptance and remaining layout integrations are tracked in callable-containers-integration.md. Direct callable arrays remain a missing capability discovered during S05. Implement them against the same recursive value type representation; do not present clearer rejection diagnostics as storage support. Existing callable access, once and owned contracts must survive storage, extraction and invocation. Optional native argument adaptation remains tied to registry identity and the destination callable contract.

[Callable container integration gates](callable-containers-integration.md) now map the actual resolver, checked-type, ownership, emitter, clone and array-operation boundaries. Owned callable field storage is implemented with focused evidence; direct callable arrays and remaining layout/cleanup integrations are still required. Generic callback inference/editor work and its registered workloads do not satisfy those remaining requirements.

## Current integration points

syntax.rs retains structured ValueAnnotation trees for fields, locals and signatures. ParameterAnnotation and ResultAnnotation still retain legacy callable wrappers alongside this tree. Type includes origin-specific Closure/Callback variants. Module linking remaps nominal names and callable annotations; emitter/storage/record runtime consume checked type identities. These structures must evolve together rather than encode generic/callable types in ad hoc token text.

## Implementation increments and gates

1. **Recursive source annotations.** Introduce a shared, span-preserving value annotation AST for named types, generic applications, array/grouped/nullable types and callable contracts. Retain distinct parameter access and result semantics. Parse type parameter declarations and explicit type arguments without confusing comparison, shift or arrow tokens. Migrate records, locals, function parameters/results and module remapping. Existing programs, source coordinates and quick fixes retain behavior. New unsupported semantic forms remain source diagnostics until their checking increment lands.
2. **Type identity and substitution.** Intern checked applied types using declaration identity plus ordered arguments. Type variables resolve lexically and cannot leak across modules or shadow nominal records accidentally. Validate arity, duplicate/unbound parameters and recursive/expanding applications. Substitute through nested arrays, records, nullable members and callable contracts while preserving access/once metadata. Add nominal alias/module fixtures and deterministic identity tests.
3. **Bounded function specialization.** Infer substitutions from checked arguments and expected result where justified; support explicit arguments for ambiguous calls. Cache each concrete specialization by definition and type arguments. Recursive concrete calls reuse an in-progress specialization; expanding recursion stops with a source diagnostic. Define and document finite per-definition and program-wide specialization budgets before acceptance; never widen the compiler stack limit. Generated monomorphic code executes for scalar, string, record and nested-container cases at optimization levels 0 and 3. Frontend operation requires no backend.
4. **Callable container representation.** Resolve callable annotations in fields/array leaves, retaining invocation modes and result identities. Support field/index calls and checked moves, borrowed access and mutable replacement. Specify heterogeneous origins through a common checked callable representation rather than assuming one closure ID. Test capture lifetime, repeated/once invocation, mutation during loans, extraction/transfer, cleanup of replaced values and exact diagnostics. Preserve imported native signature/optional adaptation and local shadowing. This is a required capability, not optional follow-up.
5. **Result construction and observation.** Freeze public syntax and typed success/error constructors before adding catalog entries. Check that each constructor initializes only its active payload; require enough explicit/contextual type information to determine both parameters. Expose a stable discriminant and branch-proven payload access. Do not expose uninitialized inactive fields or permit unchecked payload reads. Verify scalar/string/record/container/callable payloads, nullable payloads and native integration without hidden cloning.
6. **Flow, propagation and cleanup.** Narrow stable named result places using the accepted discriminant. Replacement or transfer invalidates the proof. Specify early-return propagation as explicit typed control flow first; shorthand syntax requires separate accepted checking/emission. Verify exhaustive success/error handling, joins, nested returns, callbacks, recursion, loans and drop-on-error/partial construction. No implicit throwing behavior.
7. **Registry and editor parity.** Extend NativeType to structured type applications/variables only after checked identity exists. Native errors use ordinary Result data. Completion, hover, signature help, navigation, generics and branch-narrowed payload types use current checked metadata. Every new constructor/property has full behavioral documentation and executable examples before acceptance; development provenance stays outside hover. Preserve unsaved project freshness and guarded edit rules.
8. **Acceptance and checkpoint registration.** Focused positive/negative compiler, generated native, ownership/drop, editor and copied-CLI witnesses for each increment. Register equivalent observable generic/container/result workloads and frontend-specialization scaling workloads; compare direct Rust where native wrapper cost matters. Record separate pending measurement status and preserve originals in SQLite at the scheduled checkpoint. Do not claim general library coverage from one constructor or parser test.

## Decisions required before public API acceptance

Freeze Result source syntax, constructor inference/explicit arguments, discriminant and payload naming, and propagation behavior with runnable examples. ## Shared structured type substitution — function specialization prerequisite

The isolated type_substitution.rs component substitutes concrete lexical arguments through groups, arrays, unions, applied records and callable signatures.
