# Milestone 49: native transcendental, power, and magnitude functions

[Roadmap](../roadmap.md) · [Number coverage](../guides/language/feature-coverage.md)

## Scope

Add nineteen unary Math functions: acos, acosh, asin, asinh, atan, atanh, cbrt, cos, cosh, exp, expm1, log, log10, log1p, log2, sin, sinh, tan, and tanh. Add binary `atan2(y, x)` and `pow`, and explicit variadic `hypot`. All arguments and results use primitive `number` with existing contextual literals and explicit int conversion.

Use ordinary Rust f64 methods. Evaluate every argument once in source order before computing the result, including later hypot arguments after NaN or infinity. Hypot uses an ordinary stack argument array and standard `hypot` folding; empty input returns positive zero and any infinity takes priority over NaN. Power preserves zero-exponent, NaN-exponent, and unit-base/infinite-exponent distinctions with small guards, then uses `powf`. Do not replace it with integer exponentiation or a custom numerical algorithm.

Rust's native precision may differ from JavaScript's final bits. The [standard f64 documentation](https://doc.rust-lang.org/std/primitive.f64.html#method.sin) specifies platform-dependent precision for these functions. Document those differences without inventing universal error guarantees. Preserve IEEE classifications and signed zeros wherever the method contract specifies them.

## Acceptance

Focused native checks at optimization levels 0 and 3 cover type/arity diagnostics, exact argument order, ownership and captures, empty reductions, mathematical domains and endpoints, overflow/underflow, signed zeros, NaN/infinity combinations, and nontrivial finite values against independent references. Metamorphic checks supplement reference fixtures; they do not substitute for numerical validation. Run one settled full regression, retaining passed suites after any affected-case repair.

Each method receives a genuine TypeScript counterpart and whole-iteration workload. Before timing, define the numerical domain and error criterion, generate independent directed-rounding reference intervals from exact binary64 inputs, and validate actual engine output bits. Record measured error and classifications separately from throughput. Supporting ordered additions need their own error bounds when the workload accumulates scalar results. Preserve old exact IEEE protocols and their records. Do not manufacture shared exact hashes by quantizing measured outputs or choosing only special answers.

The comparison criterion is predeclared before observing engine output: at most eight adjacent finite binary64 ranks for each operation, or 32 for the four-argument hypot workload. These are falsifiable criteria for explicitly bounded ordinary inputs, not language-wide precision promises. Every engine must pass an untimed probe of every distinct input tuple before scalar timing, establishing pointwise accuracy separately from aggregate output. Actual scalar bits and error remain recorded separately for every warmup and sample. Independent intervals propagate each supporting addition in source order; timing observes the final scalar rather than every intermediate kernel result.

The pinned benchmark reference tool is separate from generated programs and compiler dependencies. Record its package/library versions, artifact hashes, generation command, precision, input bits, and [MPFR directed-rounding settings](https://www.mpfr.org/mpfr-current/mpfr.html#Rounding). Its availability alone does not establish that a new approximate validator is correct.
