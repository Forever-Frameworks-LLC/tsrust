# Exception syntax: implementation design in progress

## Current source behavior

Source programs now support `try`, `catch`, `finally` and explicit `throw`. Finally executes before a pending return, throw, break or continue completes; a completion produced by finally replaces the pending completion. Catch values follow inferred error contracts and require narrowing when alternatives differ. Arithmetic and bounds failures carry structured runtime errors with original module filename and byte offsets.

The synchronous testing runner accepts typed callback failures, runs teardown, reports failed cases and continues to later tests. Reusable callbacks removed from callable arrays can transfer into an owned test registration. That transfer must not permit subsequent use of the same environment. Ordinary concrete closure replacement restrictions remain unchanged. Single-use and shared callback registration coverage is still pending.

Gate 142 remains in progress. Historical sections below record intermediate stages and do not describe the current activation state. The latest handoff sections contain current validation and remaining acceptance work.

## Shared observable requirements

Explicit throw evaluates its value once. A thrown owner must transfer without an implicit clone. The nearest applicable catch receives the value; a rethrow propagates it to the enclosing handler. Calls propagate recoverable errors across function and callback boundaries. Successful calls retain their ordinary result and access contracts.

Catch bindings have their own lexical scope. An omitted binding discards the caught value. Finally runs on normal completion, a caught or propagating error, return, break and continue. Its abrupt completion supersedes the pending completion. Nested finally blocks run from inner to outer. Cleanup must preserve deterministic owner disposal without silently restoring a transferred value.

Ownership and definite assignment must account for error exits at the actual throwing point and at error-producing calls. A catch cannot assume statements after the failing operation ran. Successful and catch paths join separately, while finally operates on every reaching completion. Labeled control must target the original enclosing statement after cleanup.

## Typed propagation option

A Result-based backend needs error-effect contracts for functions, generic specializations and callable signatures. Catch value types must come from checked error types, including indirect and recursive calls, rather than guessed from text inside the try block. Generated function and callable result representations must remain consistent with native ABI consumers. Success and error results transfer their owned contents.

A handler boundary cannot merely be a Rust closure containing the source try block: that would change the destination of source return and prevent break/continue from reaching an outer loop. Lowering needs explicit completion variants or equivalent structured control, with finally wrapping all outgoing completions. The existing fatal checked operations stay outside recoverable propagation if that is the owner's chosen contract.

## Recoverable runtime-failure option

Recovering existing native failures requires a stable catch value and source metadata for bounds, overflow and other generated runtime errors. Those errors must be distinguished from compiler/backend defects and from std:testing assertion failures. The model must define which failures are language errors; catching every native panic would hide unrelated defects.

Using native unwinding alone does not solve ownership checking or finally on return/break/continue. Any unwind boundary still requires correct source control destinations, transfer state, initialized local storage and cleanup. No panic hook or dynamic payload representation has been selected.

## Owner clarification

The implementation must target recoverable Tsrust errors for ordinary native-operation failures, not merely deliberate throws. Prefer checked operations and explicit error propagation; broad panic interception alone is not an ownership or recovery model. Entry-boundary reporting must be controlled, and external process termination remains outside the guarantee. The owner clarified the target, not a specific backend or error-value representation.

## Async extensibility requirement

The owner explicitly requested room for later advanced async implementation. Keep the source exception AST independent of synchronous execution machinery. A pending completion needs an explicit kind and payload: normal completion, return, throw, break or continue with its checked destination. Finally transforms that pending completion; a new abrupt completion replaces the earlier one. A later async state machine must be able to retain the payload, initialized owner state and destination across suspension without changing the synchronous source semantics.

Error propagation contracts and their checked types should remain separate from scheduling and native function wrappers. Future cancellation needs a defined protocol rather than being silently equated with a native panic or destructor invocation. Async cleanup cannot be promised merely by relying on Rust Drop: cleanup that suspends needs execution support and an explicit cancellation/shutdown policy. Those future features are not implemented or accepted by this gate.

## Preliminary error-effect stage

error_effects.rs computes conservative function and closure failure summaries to a fixed point, then annotates checked expressions with may_fail metadata. Bounds access, non-null assertions and checked integer operations contribute failure effects. Number division does not introduce an integer-overflow effect. Calls use the available function/closure summary; opaque or unclassified call contracts conservatively permit failure. Creating a closure does not execute its body, so creation and invocation have separate effects. This boolean metadata is preliminary: it is not a typed error union, a complete native-failure classification or proof that native panics cannot escape. Catch handling currently remains conservative in function summaries.

Definite assignment consumes the metadata before successful assignment can initialize its target. A failed RHS preserves the incoming initialization state for catch/finally. Post-test loop condition failures use the state after the body and update; pre-test failures use the incoming state. Return-expression failure remains a throw completion distinct from successful return. The metadata and source completion identities remain independent of scheduling so a later async state machine can preserve the pending completion and ownership state across suspension.
